# 混合图文请求的视觉编码干扰 · 前期探索方案

2026-11-06 · 单卡机制 pilot · 待用户手动开启 goal 后执行

## 1. 问题与假设

同一张 RTX 4090 上，同一个 VLM 实例正在给纯文本请求生成 token。一条图文请求加入时，移除它的视觉塔前向，能否降低这些在途文本请求的输出间隔尾部？进一步用同批次时间线判断，减少的等待主要来自视觉 GPU 工作，还是塔内的主机准备、拷贝或同步。

**主假设**　在固定单图负载和运行配置下，保留原图输入、媒体预处理、图文请求的语言模型工作及调度规则后，以同源预计算特征替代在线视觉塔前向，会使在途纯文本的服务端尾部输出间隔下降至少 **3 ms 且 15%**。能否把差值归到 GPU 视觉计算，还要通过阶段证据验收。门槛是本次 pilot 的工程投入阈值，适用范围为这一配置和负载。

**已有工作**　TriInfer 的 §3.2 和图 4 已经描述在途 decode 被图像编码和 prefill 延迟，也指出仅限制 LM token 数容易漏算图像编码。§4.2 已分别使用图像和 token 预算，§5.6 已测双 CUDA stream 的并行收益。其主要集群评估用 4 台各 8 张 H20 的服务器，重点是混合 EPD 放置、分阶段批处理和达标吞吐。这里先在消费级单卡和固定引擎上做同一图文请求的阶段消融，作为后续选题的可行性证据。作者仓库当前只有说明和许可证。[TriInfer 正式论文](https://proceedings.mlsys.org/paper_files/paper/2026/file/f068c65585985c25c17f221390774ec7-Paper-Conference.pdf) · [作者幻灯](https://mlsys.org/media/mlsys-2026/Slides/3756.pdf) · [作者仓库](https://github.com/dongxianzhe/triinfer)

## 2. 固定版本与旁路落点

- **选卡**　两张卡均为 RTX 4090。用户确认负载时 GPU0 实际协商为 PCIe Gen4 ×16，GPU1 为 PCIe Gen4 ×4。单卡主实验优先用 GPU0，GPU1 仅用于满足第 4 节条件时的独立重复。执行时按 GPU UUID 与 PCI bus ID 确认设备，记录各自负载时的实际链路代际和宽度。
- **模型**　`Qwen/Qwen3-VL-2B-Instruct`，BF16，固定 revision `89644892e4d85e24eaac8bacfd4f463576704203`，模型、tokenizer、chat template、processor 用同一快照。权重文件约 4.26 GB。按 28 层、8 KV heads、head dim 128、BF16 估算，KV 约 112 KiB/token，8,192 token 池约 0.875 GiB。另计页对齐、预留池、视觉激活和运行时工作区。4090 兼容性及实际峰值由预检确认。[固定快照](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct/tree/89644892e4d85e24eaac8bacfd4f463576704203) · [模型配置](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct/blob/89644892e4d85e24eaac8bacfd4f463576704203/config.json)
- **引擎**　vLLM V1 `v0.33.0`，上游 commit `4ba787ec9959e566d3b587a796dff07673324da5`。单 API server、单实例、TP/PP/DP=1，只暴露 GPU0 UUID，loopback 服务。首轮统一 eager（`--enforce-eager`），关闭视觉图捕获和异步调度（`--no-async-scheduling`），固定 LM 与 ViT attention 后端、KV dtype、流式设置、chunked prefill 配置，关闭投机、卸载、跨请求前缀复用和 MM processor cache。起始上下文上限 2048、并发上限 8、每步 token 预算 2048。优先设置 `--kv-cache-memory-bytes 939524096`（0.875 GiB），记录块对齐后的有效容量，验证至少容纳本 trace。实际导入路径、版本、依赖和生效配置均需留档。采用 eager 和合成 trace 是为缩小归因范围。[vLLM 发行版](https://github.com/vllm-project/vllm/releases/tag/v0.33.0) · [该版引擎参数](https://docs.vllm.ai/en/v0.33.0/configuration/engine_args/)
- **源码路径**　V1 scheduler 按占位区间、encoder cache 和预算决定是否下发视觉输入。GPU runner 在 `_preprocess` 中先 `_execute_mm_encoder` 再收集视觉特征、合并嵌入并交给 LM。Qwen3-VL 图像像素分支调用 `self.visual`，该塔输出按列拼接主特征和三个 DeepStack 层。下游按图像网格拆分，再按占位与 M-RoPE 组装 LM 输入。这给出了一个能保留调度和 LM 路径的实验切点。[V1 scheduler](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/v1/core/sched/scheduler.py#L1875) · [GPU runner](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/v1/worker/gpu_model_runner.py#L3000) · [Qwen3-VL 视觉塔与输入分支](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/model_executor/models/qwen3_vl.py#L801)
- **引擎也接受预计算特征**　公开 Python 入口支持 `enable_mm_embeds=True`，Qwen3-VL 图像字典需要 `image_embeds` 与 `image_grid_thw`。预计 BF16 张量为 `[N, 8192]`，含 `4 × 2048` 通道，`N = prod(grid_thw)/4`，以实际视觉塔输出为准。源码将其转换为塔的 dtype 后直接拆分，省掉 `self.visual`。公开入口可做功能交叉检查，但改变上传、媒体解码、处理器与输入张量传输。正式对照走同一原图接口，在 worker 内替换。[vLLM 多模态输入](https://docs.vllm.ai/en/v0.33.0/features/multimodal_inputs/#passing-multimodal-embeddings) · [预计算分支](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/model_executor/models/qwen3_vl.py#L2260)

## 3. 三个实验臂与预检门槛

| 臂 | 在同一 VLM 实例上做什么 | 用途 |
|---|---|---|
| T | 四路纯文本已在生成，记一个空到达槽 | 估计无图文加入时的尾部与自然波动 |
| R | 同样四路文本，加一条原图请求，完整在线视觉塔 | 基线混跑 |
| B | 与 R 相同的原图请求，原图仍解码、预处理并按同一路径传入 GPU。视觉塔前向返回同源的 GPU 驻留特征 | R−B 估计在线视觉前向对文本尾部的边际影响。B−T 描述图文加入后仍存在的差异 |

**干预实现**　仅修改本实验的引擎副本。提前用同 worker、同权重与处理器、同 dtype/后端、单图形状捕获完整视觉塔输出，预热阶段校验后驻留 GPU。R 和 B 持有同一份常驻特征及同样的插桩，R 正常前向，B 在原像素张量的 device move 执行后返回预计算结果。塔内位置元数据准备、额外拷贝和同步可能随前向一起被省去，分别计时并按实际切点限定归因范围。校验时记录像素与特征哈希、形状、dtype、布局、图像 ID 和网格。热路径用经预检验证的内部 ID 和形状做匹配，避免当场读取 GPU 数据来计算哈希。查不到特征、实际 encoder batch 形状不同或意外缓存命中时显式记为失败。沿用原来的 encoder 调度、输出入缓存及特征收集路径。禁止为了旁路更改 KV、去掉图文请求、减少图文输出或预先跳过 LM prefill。[视觉塔入口及元数据准备](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/model_executor/models/qwen3_vl.py#L713)

**正式回放前核验**

1. 分别跑纯文本、原图及旁路单请求，再用同一混跑探针验证。未插桩原始路径与 R 的固定样本输出和调度形状应一致。R 与 B 核对相同图像字节、`pixel_values`、`image_grid_thw`、展开后的 prompt IDs、占位区间、M-RoPE positions/delta、实际送入 LM 的主/DeepStack 特征、KV 新增 token 及每步 prefill 分片。特征做逐元素校验，同路径自然数值波动先重复实测。隔离 greedy 图文样本的输出 token IDs 应一致。混跑中的输出差异须保留首个分歧和批次证据，出现稳定的臂间内容偏移则等价验收失败。
2. R 与 B 每次图文加入均有一次正常 encoder 调度，R 实际跑视觉塔，B 实际命中实验驻留特征。检查没有可复用的跨请求 LM 前缀或原生视觉缓存命中，保留单请求内部的正常 encoder 缓存。每 episode 使用新请求 ID，核对 scheduler 实际使用的 MM key 及回收状态，防止预热或前一轮绕过预定路径。记录每步实际调度的未命中 LM token、视觉占位/特征 token、活跃 decode ID 和上下文长度、LM batch 形状与重排。统计开关和采样代码三臂一致。
3. 图文进入第一个混合步时，两臂都须有四个在途文本请求。按 episode ID 比较该步及后续 prefill 分片的图文 token 数、decode 批大小和后端，图文首个混合步中对应文本的已生成 token 序号差预设最多 2。若到达抖动频繁打破匹配，预检允许调整一次触发偏移，复检后冻结。正式数据完整保留，另给匹配子集及不匹配比例。主结论要求至少 90% 的 R/B 配对 episode 通过该匹配，且全量与匹配结果同方向。
4. 若完整前向旁路有无法拆开的塔内拷贝、同步或主机准备，可在预检预算内将切点移至共同完成 patch embedding、位置元数据和位置嵌入之后，仅跳过视觉 blocks 与 mergers。重新验收并冻结单一切点，结论相应限定为该计算段。若仍无法证明等价或定位阶段，降级为 T/R 的阶段相关性筛查，最多三个配对块。公开 embedding 入口或等 LM 长度的文本替代可以帮助排查，但二者的差异均不能单独归给 GPU 视觉计算。

## 4. Trace、重复与指标

**一次 episode**　四条固定纯文本 prompt，各约 256 个实际输入 token，错开内容、同期开流。温度 0、忽略 EOS、每条固定生成 192 token。以客户端从预先指定的一路文本累计收到至少 16 个输出 token ID 的时刻作为触发点，预检核实 `return_token_ids` 的流式语义，确认其余三路已开始输出，按固定偏移发出图文请求或记空槽。相对触发点的发送计划冻结，记录实际偏移和各流当时的 token 序号。图文负载为一张固定分辨率的 RGB PNG 加一个固定问题，生成 16 token。起点为 768×768，按配置预计 grid `[1,48,48]`、576 个视觉占位 token，以实际 processor 输出为准。用固定 seed 在本机生成 4 张相同尺寸的几何图，轮换使用，保存生成规则、原始字节和哈希。每个 episode 排空后再开始下一个。预检只允许为资源或覆盖门槛调整一次共同设置，记录原因并在正式回放前冻结。只用一个图像尺寸与一个并发度做正式比较。

**重复**　GPU0 做 6 个配对块，每块 16 个 episode × 三臂，共 288 个 episode。每块三臂使用同一批 trace 和 seed，六个臂序各出现一次，预先固定顺序。每个块先跑相同短预热，换臂仅在排空后切换，优先复用同一进程和同一有效配置。GPU1 只在 GPU0 有可解释、可重复的信号且总预算仍余至少 25 GPU 分钟时做两块独立重复，两块反转 R/B 次序，三臂与 trace 同定义。结果按卡和负载链路配置单列。

**主要指标**　以实际发图时刻或 T 臂对应空槽时刻为锚，预设观测窗为锚前 50 ms 至锚后 400 ms。纳入与窗口相交的四路在途文本的连续服务端 token 就绪间隔，每 episode 取最大值，再按块和臂计算这些最大值的 P95（固定线性插值）。用就绪事件和 token 索引确认确实有四路覆盖整窗，并确认图文首个混合步落在窗内。预检可因窗口覆盖不足调整一次窗或统一输出长度，随后冻结。主对比是每块 R−B 的 P95 差值和相对 B 的变化率。分块报告 6 个配对差、中位数和范围，附 96 个 episode/臂的描述性汇总。请求与 token 间隔共享调度步，统计重复单位为配对块。另报全流间隔 P95/P99、固定窗前的纯文本间隔、按相同调度步匹配的文本 gap、图文 TTFT、失败/超时率及已完成量。

**区分卡顿发生在哪一段**

| 记录 | 时间边界及粒度 |
|---|---|
| 客户端与入口 | 同机单调时钟记录计划/实际发送、接收请求、Base64 与 PNG 解码、resize/归一化、tokenizer/processor、engine 入队、首次调度。阶段按 RID 对齐。 |
| GPU 传输与执行 | 记录实际 pixel/grid/metadata 拷贝与视觉塔前向。少量独立诊断 episode 用 CUDA events 加 NVTX/CUDA 时间线核实 stream、H2D/D2H、同步、GPU kernel 与空档。CUDA events 在排空后读。视觉区间历时单列，GPU kernel 时间以活动轨迹为准。 |
| LM 与服务端输出 | 按 iteration 记录 LM forward、prefill 与 decode token 组成、图文与文本 RID、采样完成及首个新 token 交付输出队列的时刻。一个 mixed forward 有共享耗时，记录其批次组成和整体时长。通过 RID、iteration 和 token 序号关联 GPU 事件与 token 就绪。 |
| 流式输出 | 同时记服务端输出队列至 SSE 发送、客户端原始 SSE 到达和每事件新增 token 数。多 token 合包或空增量单列，客户端统一报告 SSE 输出间隔。只有逐 token 就绪证据才用于主指标。 |

正式回放只保留轻量计时与批次记录。诊断轮在预算内各取 R、B 一小段，同时检查低开销插桩对 R 的影响。判断同一步中是视觉阶段占用顺序执行的时间、真正的 GPU kernel 并发争用，还是队列、输出处理或其他因素。若阶段轨迹不足，只报告已验证的视觉前向切点效应或相关性，并注明细分归因缺失。

## 5. 预算、判定与停止

- **总上限 120 GPU 分钟**，累计两个设备实际为本实验占用的时间，含启动、预热、特征生成、预检、失败、重复及收尾。分配 35 分钟预检、55 分钟 GPU0 正式回放、30 分钟诊断、可选 GPU1 与收尾，最后 5 分钟专供释放和复查。单次启动就绪上限 5 分钟，每臂每块含排空上限 3 分钟，单请求无输出进展 15 s 或总时限 30 s 记失败。执行总墙钟预算 4 小时，含环境准备和下载。达到总预算、GPU 显存总占用 20 GiB、实验进程树 RSS 48 GiB，或出现 OOM、Xid、外部作业占卡时，停止本实验作业并保留证据。
- **支持主假设**　至少 5/6 个配对块 R−B 为正，差值和相对变化的块中位数分别达到 3 ms 和 15%，通过输出、批次与缓存验收，且图文加入前的 R/B 差异小于主效应，无法解释观察到的差值。至少在 R/B 诊断轨迹中对齐导致长 gap 的混合步，核实被省去的 GPU 视觉工作与该步缩短相符，并检查媒体解码、拷贝、LM 时长、队列与 SSE 是否足以解释差值。阶段证据不足时分开报告端到端差值和归因缺口。即使 R−B 过门槛，也报告 B−T 的残余和混合 LM 步证据，以判断视觉编码能解释多大范围的卡顿。
- **可测条件下未过门槛**　有稳定视觉执行和混跑重叠、等价通过且重复噪声小于工程门槛，但差值稳定低于门槛或方向相反，结束当前配置的视觉编码切口。重复噪声大、窗口覆盖不够、关键证据缺失或差值跨越门槛时，记为未判定。首轮结果只适用于实际负载、版本、eager 和设备，作为下一轮是否值得投入的依据。
- **失败处理**　保留每条提交的终态与原轮。记录发出偏差、阶段缺失、调度不匹配、HTTP/协议失败、卡顿与进程退出。按固定规则列出可测样本和全部失败数，禁止将失败伪装为零延迟。只有明确外部故障或采集失效可在原预算内补跑一次整个配对块并单列原轮，仍缺块时不套用 5/6 门槛。预算用完、旁路无法验收或仅得到不稳定相关性时按原计划收尾。首轮结束后交付证据，编码配额或其他调度策略留待下一轮决策。
