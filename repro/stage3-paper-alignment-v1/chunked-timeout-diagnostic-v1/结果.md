# Chunked 超时请求隔离诊断

日期：2026-10-28。目的：判断 E2 chunked 组的失败响应是否由请求内容/长度本身导致，或只在80请求突发并发下出现。此诊断不是性能数据。

## 方法

- 在 RTX 4090 GPU1 启动同一作者fork的 `sglang-fork-chunked-2048` 配置，并核对 `server-info` 与 E2 相同。
- 执行原矩阵相同的 E1 seed101 60请求预热，然后 `flush_cache`。
- 从固定 E2 workload 原样抽出两个失败请求，分别单请求复放：seed101/request9（输入1558，目标输出2328）；seed102/request66（输入1428，目标输出1940）。保留相同 token ID 与 `ignore_eos`/采样参数行为。

## 结果

| 请求 | E2突发下 | 单独复放 | 单独运行时间 |
|---|---:|---:|---:|
| seed101/request9 | 超时；最后已报告1693/2328 token，最后事件71.24s | 1/1完成 | 87.27s |
| seed102/request66 | 超时；最后已报告970/1940 token，最后事件143.45s | 1/1完成 | 72.73s |

两条复放使用不同的一请求 workload 文件哈希，但每条内部的 prompt token 和目标输出长度都与冻结 E2 文件完全相同。客户端、服务端日志、server-info、预热与完整SSE都保存在本目录。

## 解释边界

- `[观察]` 两个原失败请求在相同 chunked 配置下单独完成，排除了格式错误或单个输入长度必然无法完成的解释。
- `[观察]` 80请求 E2 失败时，服务端退出日志列出的剩余 request ID 与未完成 SSE 请求完全一致。三个 chunked seed 的常规 KV retraction 事件/请求数分别为8、12、7；seed103虽有7次也完整结束，因此 retraction 数量本身不能解释哪条请求停滞。
- `[源码事实]` `ScheduleBatch.retract_decode`会释放被选请求的KV；scheduler随后将这些请求重新加入等待队列。E2 日志只记录每次回收数量，没有记录具体 request ID 的 retraction、重新入队、再调度和完成链路。
- `[推断]` 故障依赖高并发突发时的调度/回收状态，或客户端连接在该状态下的流式进度；目前还不能区分SGLang scheduler重调度问题、请求状态问题或传输/回放器行为，也不能将效果归因于TokenFlow。

下一步若需要根因，需在短期诊断补丁中按 request ID 记录 `retract_decode`、waiting queue入队、prefill重调度、decode继续和finish/abort五个事件，并复跑冻结的 E2 seed101；补丁运行不混入性能数据。
